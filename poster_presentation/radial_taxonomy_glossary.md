**Then:** "canopy cover" no longer says "(Canada-only)" anywhere. A first attempt at enlarging the thumbnails just pushed them further out (`thumb_gap` 0.05→1.0) — technically bigger, but that's not really "enlarging," it's "making more room by adding empty space," and it was rightly called out as not the same thing. Archived as `_archive_old/radial_taxonomy_v4_far_thumbs.png`.

**Then, the actual fix:** thumbnails are now drawn **rotated to point radially outward** — long axis along the radius, short axis tangential — instead of axis-aligned squares. This decouples the two dimensions that used to be locked together: tangential *width* is the only dimension that can make neighbours collide, so only it is solved against the arc available at the inner placement radius (same no-overlap solver logic as before, just applied to one axis); radial *height* has no neighbour to collide with (every petal points straight out from the centre), so it's a free parameter — `--thumb-height` defaults to 0.4, roughly triple the old fixed square size, with zero risk of overlap. This is what "enlarge the samples, not the distance" actually meant. Verified by cropping a zoomed region and confirming the thumbnail border rectangles are visibly tilted (not axis-aligned), i.e. the rotation is real, not just an aspect-ratio coincidence. Prior wheel version archived as `_archive_old/radial_taxonomy_v4_far_thumbs.png`; earlier ones as `radial_taxonomy_v3_thin_rings.png`, `radial_taxonomy_rings_v2.png` (pre-native-dendrogram), `radial_taxonomy_combined.png` (compositing-era).

New/renamed CLI flags on `build_radial_rings.py`: `--thumb-width` (was `--thumb-size`, now tangential-only, auto-shrunk for no overlap) and `--thumb-height` (new, radial length, free to enlarge).

**One more round after that, comparing directly against the actual source-paper figure:** two more real problems, both fixed:

1. **Sampling method.** Each thumbnail was clipping only the buildings belonging to one statistically-selected morphotope, padded with generous whitespace -- an isolated, sparse-looking silhouette, not a real place. It's now a **fixed 350m×350m window centred on that morphotope's centroid, pulling in every building nearby** (not just cells belonging to that exact morphotope) — reads as an actual neighbourhood sample, dense and full-frame, matching how the source figure's thumbnails look. Window size is a CLI flag (`--sample-window-m`) — 350m, 500m, and 800m were all tried side by side; 350m won for density and consistency (800m occasionally caught a single isolated large building with mostly empty space around it).
2. **Border boxes removed.** The thin grey frame around each thumbnail is gone — they float directly on white now, connected only by the leader line, matching the source figure exactly (its thumbnails have no visible frame either).

**One more round: per-region adaptive scale, not one fixed window for all 32.** Comparing again against `_archive_old/radial_taxonomy.png` (an early pass), its thumbnails visibly vary in density — some sparse, some packed — because that scale was data-driven per region, not a single uniform crop. The fixed-350m version above was authentically dense everywhere, but that's not honest for a low-density fabric type; it just crops in tight enough to hide the emptiness.

Fixed by analyzing each representative morphotope's own real extent *before* choosing its window — checked the actual data first (the 32 representative morphotopes' natural size ranges from ~510m to ~5870m across, median ~1820m — nowhere near uniform), then derived each thumbnail's window from that specific morphotope's own bounding box (+15% padding), clamped only at the extremes (`--sample-min-window-m` 250, `--sample-max-window-m` 2500) so nothing zooms in absurdly close or out to near-nothing. A dense, compact fabric type now genuinely reads as dense; a sparse, spread-out one genuinely reads as sparse — because that's what's actually there, not an artifact of one crop size applied to everything. Old fixed-350m version archived as `_archive_old/radial_taxonomy_v6_fixed350m.png`.

**Then: fragmented morphotopes.** Some of the 32 representative morphotopes turned out to be spatially split into several disconnected patches (checked directly: 5 of 32 have >1 connected component, 3 of those split roughly 50/50 or worse). The previous version's "pull every building in the bounding-box window" approach, applied to one of these, pulled in the gap between patches too — several separate clumps of buildings scattered across one thumbnail with a lot of empty space between them, exactly what got flagged. Fixed the way you described it: split the morphotope's own cell geometry into connected components and keep only the largest one (most cells) — "if a cluster has 3 locations in a region, show the one with the best visibility," not all three stitched together. Verified against the actual data (not just eyeballed) before shipping it. Border-box removal from the previous round is unaffected/still in place. Old fragmented-sample version archived as `_archive_old/radial_taxonomy_v7_adaptive_fragmented.png`.

**Then: the rectangular-box complaint, understood correctly this time.** Every version up to this point — even after fixing fragmentation and picking an adaptive per-region scale — still queried `buildings.gpkg` with a literal rectangular bbox and showed *every* building that happened to fall inside it. A real urban grid fills a square window edge-to-edge, so the result always read as "a rectangular chunk cut out of the city," and a building sitting right at the window's edge would be sliced in half. That's what "no rectangular boxes" actually meant — not a border line (already removed two rounds ago), the sampling method itself.

Fixed properly: the morphotope's own tessellation-cell geometry (organic, Voronoi-like shapes around real buildings, never a rectangle) is unioned into the true sampling region; only buildings whose centroid genuinely falls inside that organic shape are kept — every one shown is a complete, uncut footprint, and the sample's outer silhouette is that morphotope's own natural boundary, not a box. When a patch has too many cells to be a clean single sample, the fix is "take a sample of *that same morphotope's* cells" (nearest N to its own centroid — a real spatial subset) rather than widening the crop into a bigger window. The plot's own axes are then set to the selected buildings' actual bounds with a small margin, not a fixed/uniform window size. Verified by cropping to full resolution and checking that footprints have real, irregular edges with nothing sliced off. Old bbox-cropped version archived as `_archive_old/radial_taxonomy_v8_bbox_cut.png`.

**Then: cleaned up the connector styling.** Removed two things — the dotted leader line running from the ring edge to each thumbnail's centre, and the separate faint grey "ceiling" circle that traced the outer edge of the abundance ring. In their place: the same white radial dividers that already separate the wedges (hub → ring edge) now continue as a plain grey line from that exact same point (the ring's own outer edge, not the centre) on out toward the thumbnails. One continuous divider system instead of three separate decorative elements doing overlapping jobs.

**Then: dividers corrected to stop exactly where the footprint ends.** First attempt ran a fixed amount past every thumbnail's box regardless of its real content — overshot badly whenever a thumbnail's actual aspect ratio made it much shorter than the box ceiling (`thumb_height`), since that overshoot was computed from the box, not the image. Fixed by tracking each leaf's REAL rendered length (`disp_h`, already computed once per thumbnail for placement) and using the longer of the two neighbouring leaves' actual lengths as each divider's endpoint — so it stops right at real content, not a generic formula.

## Why the earlier compositing approach was dropped

Two rounds ago, the dendrogram was rendered as its own image (`build_radial_dendrogram.py`) and pasted into this script's open centre via a third script (`build_radial_composite.py`), with the scale/position computed algebraically from each script's known geometry. It was correctly aligned, but you flagged real problems with it: the rings took up too much space and the pasted-in dendrogram read as small and unclear, the footprint thumbnails were overlapping, and you suspected the paste/clip approach itself was part of the problem.

Rather than keep patching the composite, **the dendrogram is now drawn directly into the rings script's own Axes** — same data coordinates, same leaf order (derived from the dendrogram tree itself, not a separate synced file), same angle convention. There's no scaling, no pasting, no seam. `build_radial_dendrogram.py` and `build_radial_composite.py` still exist and still work (e.g. if you want a plain dendrogram figure on its own), but neither is needed to build the main figure anymore.

## What changed, concretely, to fix your three complaints

1. **"Rings taking too much space / central dendrogram not clearly visible"** — the open centre (`hub_r`) is now bigger relative to the whole wheel (0.42 vs. the original 0.30, tuned again in this round), and because the dendrogram is native vector content instead of a small pasted raster, its lines and leaf dots render crisp at whatever size the centre actually is — nothing lost to image resampling.
2. **"Outer footprints overlapping"** — thumbnail size is no longer a fixed guess. It's now solved for directly: given the placement radius and the number of leaves, the script computes the largest thumbnail size that leaves ~18% visual gap between every adjacent pair (`safety = 0.82` in the code), and shrinks from your requested `--thumb-size` if needed to guarantee that. No manual re-tuning by trial and error.
3. **"Small leg lengths at the outer part of the dendrogram"** — the depth-easing power (`gamma`) that controls how much radial room each hierarchy level gets was the live app's own default, 2.2, which (by design, in the app) compresses the outer/fine branching a lot to give early splits more room. For this print figure, the default here is now **1.35** — a flatter curve that gives the outer levels visibly longer, more legible legs. Exposed as `--dendro-gamma` if you want it flatter/steeper still.

A fourth, related fix: the **outer branch-colour tick ring was removed**. It was purely redundant — the dendrogram's own branch colours already convey which of the 8 fabric types each leaf belongs to, so a whole extra ring repeating that information was one more thing competing for space. Its job is now done by a proper **"Fabric branch" legend** (colour swatch + "Cluster N" label, in its own dedicated legend column on the left — not overlaid on the wheel, so it can't collide with the thumbnails the way a fixed-fraction legend did once the wheel grew).

## Component reference

**Dendrogram** (drawn inline, not a separate file): same data (`urban_taxonomy_viewer/public/data/global_cluster_summary.json`), same D3 layout math (`easeOutPow` depth→radius remap, radial-leg-then-arc links), same Bold colour ramp as the live viewer — ported and verified in an earlier round (leaf counts per cluster matched the app's own sidebar exactly). Truncated to `level_5` (32 leaves) so it shares the rings' exact leaf set and order by construction — the leaf order literally comes from walking this same tree, not a separately-maintained file.

**5 character rings** (innermost out): building area (Oranges), building compactness (Blues), coverage area ratio (Purples), distance to neighbouring buildings (Greens), canopy cover fraction — Canada-only (YlOrBr/gold). Continuous full-region wedges (not a grid of boxes), divided only by thin white radial spokes. Picked over the original 5 candidates for genuinely informative spread — see `legend_*.png` below.

**Abundance ring**: log-scale morphotope count per leaf, kept as a bar (not a full region) so its height stays legible as a value, with a faint grey ceiling guide.

**Thumbnails**: one real building-footprint silhouette per leaf (the morphotope with the largest `limAre` in that leaf), pulled from that morphotope's own region's `buildings.gpkg`, connected by a dotted leader line. Auto-sized to guarantee no overlap (see above).

**Legends**: "Fabric branch (level_3)" — 8 colour swatches, own column, replaces the old redundant tick ring. "Morphometric character rings" — 5 colour-ramp swatches with labels.

## Character legends — `assets/figures/legend_*.png`

Unchanged this round. Five standalone histograms (one per ring character), picked for real informative spread — not just because the source paper used similar ones. Two candidates with genuinely degenerate distributions at the morphotope level (`street meshedness`, 43% exactly zero; `inter-building distance`, 98.4% exactly zero) were dropped in an earlier round in favour of `coverage area ratio` and `distance to neighbouring buildings`, both clean.

## Tuning knobs (CLI flags on `build_radial_rings.py`)

`--hub-r`, `--ring-w`, `--abund-gap`, `--abund-width`, `--thumb-gap`, `--thumb-size` (rings/thumbnail proportions — thumb-size is a ceiling, auto-shrunk if needed) · `--dendro-gamma`, `--dendro-min-r-frac` (dendrogram shape) · `--level` (leaf level, default `level_5`/32) · `--dendro-data` (point at the `_nochm` viewer JSON) · `--no-thumbnails` / `--force-thumbnails`.
